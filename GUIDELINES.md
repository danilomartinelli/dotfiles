# Engineering guidelines

Reference for changing, validating, and publishing this personal macOS
dotfiles repository safely.

## Purpose and precedence

These guidelines define repository engineering contracts. They are written for
the owner and experienced coding agents who need to evolve the setup without
breaking machine installation, shell startup, configuration ownership, or
credential boundaries.

Use the documentation according to its purpose:

1. Explicit user instructions define the requested outcome and override
   repository defaults.
1. `AGENTS.md` gives repository-wide agent workflow instructions.
1. This file defines the detailed implementation and safety contracts.
1. `README.md` documents installation, operation, and the public shell surface.
1. Topic documentation such as `opencode/README.md` owns detailed procedures
   for that subsystem.

Do not duplicate a full command catalog here. Keep user onboarding and everyday
operation in `README.md`.

## Sources of truth and safety boundaries

| Concern              | Authoritative source     | Rule                                                    |
| -------------------- | ------------------------ | ------------------------------------------------------- |
| Homebrew software    | `Brewfile`               | Declare taps, formulae, casks, fonts, and MAS apps here |
| Runtime tools        | `mise/config.toml`       | Declare runtimes and language-package CLIs here         |
| Runtime resolution   | `mise/mise.lock`         | Generated by Mise; never edit by hand                   |
| macOS preferences    | `_macos/defaults.tsv`    | Catalog changes are reviewed and tested as data         |
| Topic classification | `_scripts/topic-catalog` | Setup, startup, and docs share this classifier          |
| Setup orchestration  | `_scripts/setup`         | Keep phase ordering out of public adapters              |
| OpenCode workspace   | `opencode/`              | Version only explicitly dotfiles-owned entries          |
| Public behavior      | `README.md`              | Document every command, function, alias, and dependency |

Machine-private files include `.localrc`,
`git/gitconfig.local.symlink`, SSH private keys, SOPS identities, kubeconfigs,
auth stores, OCX runtime receipts, and account identifiers. Never read their
contents into logs, tests, documentation, commits, or chat.

The repository is macOS-first and assumes interactive Zsh for normal use.
Tests should use temporary homes and fake external commands whenever possible.

## Safe change workflow

### 1. Inspect

```bash
git -c core.fsmonitor=false status --short --branch
git -c core.fsmonitor=false diff
rg --files
```

- Preserve unrelated tracked and untracked work.
- Identify the owning source, adapter, fixture test, and user-facing
  documentation before editing.
- Confirm whether a claim refers to repository source, installed local state,
  or a live external system.
- If a path may be a symlink, resolve its physical checkout before assuming
  ownership.

### 2. Edit

- Keep public adapters small and put shared behavior in the owning private
  implementation.
- Change the narrowest source of truth; do not patch generated output.
- Add or update fixture coverage with behavior changes.
- Update documentation in the same change when public behavior or ownership
  changes.
- Preserve installer idempotency and Zsh reload idempotency.

### 3. Validate

Run the focused suite first. Expand to the complete safe suite for changes that
affect discovery, setup, shared helpers, or repository-wide documentation.

Do not run `_scripts/bootstrap`, `dot`, `set-defaults`, `brew update`,
`brew upgrade`, key creation, app-opening setup, or destructive Git helpers
merely to validate source changes.

### 4. Review

```bash
git diff --check
git -c core.fsmonitor=false status --short
git -c core.fsmonitor=false diff
```

Check for unrelated files, secrets, generated artifacts, unsafe paths, stale
documentation, and missing tests.

### 5. Publish

Commit and push only with explicit authorization. Stage confirmed task paths,
use an imperative commit message, push the requested branch explicitly, then
verify divergence and cleanliness.

## Repository architecture

### Public and private roots

- `bin/` is public and added to `PATH`. A `git-foo` executable is also
  available as `git foo`.
- `functions/` is public Zsh `fpath`. Files without `_` are callable functions;
  underscore-prefixed files are internal completions.
- `tests/` is visible to humans and tooling but is explicitly not a topic.
- `tests/_support/shell-scenario.sh` owns shared fixture lifecycle, fake
  executable creation, capture, assertions, and TAP reporting.
- `_scripts/`, `_macos/`, and underscore-prefixed entries are private
  implementation excluded from topic discovery.
- `.context/`, `.codegraph/`, and `.wrangler/` are disposable local state, not
  repository configuration.

### Topic contract

A visible top-level topic may contain:

```text
topic/
├── install.sh       # Optional setup dependency phase
├── *.symlink        # File or directory linked to ~/.<basename>
├── path.zsh         # PATH configuration, loaded first
├── aliases.zsh      # Main shell configuration
├── env.zsh          # Main shell configuration
├── completion.zsh   # Loaded after compinit
└── *.zsh            # Other visible shell configuration
```

Exact rules:

- `_scripts/topic-catalog <repository-root>` is the single classifier used by
  setup, Zsh startup, and documentation coverage.
- It emits sorted `kind<TAB>absolute-path` records with kinds `topic`, `link`,
  `installer`, `path`, `main`, `prompt`, `completion`, and `aliases`.
- `aliases.zsh` emits both `main` and `aliases`; only `zsh/prompt.zsh` emits
  `prompt`.
- Discovery ignores hidden names, underscore-prefixed names, and contents of
  `*.symlink` directories.
- Installers must be direct topic children named `install.sh` and executable.
- `homebrew/install.sh` is excluded from topic installer records because
  Homebrew has its own setup phase.
- Only `*.symlink` files and directories are linked automatically.

## Installation and lifecycle contracts

### Setup ownership

`_scripts/setup` is canonical:

- `bootstrap` creates private templates and Git identity, installs links,
  applies macOS defaults, ensures Homebrew, reconciles `Brewfile`, and runs
  topic installers.
- `update` repairs checkout resolution, attempts `git pull`, restores a missing
  private environment template, conservatively repairs missing links, updates
  Homebrew, reconciles declarations, and reruns topic installers. It does not
  reapply macOS defaults.
- `checklist --open-apps` is the only intentional app-opening path. It requires
  an explicit opt-in from an interactive terminal.

`_scripts/bootstrap` and `bin/dot` are stable adapters. Required phases stop on
failure. Checkout pull, Homebrew update/upgrade, legacy cleanup, and hostname
normalization are advisory where `_scripts/setup` says so. Do not duplicate the
orchestration in adapters or topics.

`_scripts/link-dotfiles` owns interactive bootstrap linking and its fixture
batch modes. `_scripts/link-config` owns non-interactive application links with
`replace-with-backup`, `preserve-existing`, and `numbered-backup` policies.

### Installer authoring

Topic installers source `_scripts/installer-preamble.sh` immediately after
`set -e` or `set -eu`. Set `INSTALLER_ANCHOR` only when `$0` cannot identify
the sourcing file, such as a Bash script using `BASH_SOURCE`.

The preamble exports `TOPIC_DIR` and `DOTFILES_ROOT` and provides:

| Helper                      | Contract                                                                                  |
| --------------------------- | ----------------------------------------------------------------------------------------- |
| `installer_require_darwin`  | Exit successfully without mutation outside macOS                                          |
| `installer_require_command` | Fail with an actionable formula hint when a required CLI is absent                        |
| `installer_require_app`     | Warn and skip successfully when an optional app is absent; set `INSTALLER_APP` when found |
| `installer_link_config`     | Delegate application links to `_scripts/link-config`                                      |
| `installer_banner`          | Write a phase heading to stdout                                                           |
| `installer_success`         | Write successful completion to stdout                                                     |
| `installer_note`            | Write non-error detail to stdout                                                          |
| `installer_warn`            | Write a warning to stderr                                                                 |
| `installer_error`           | Write an error to stderr                                                                  |
| `installer_hint`            | Continue a warning or error with an actionable stderr hint                                |

Do not reintroduce per-installer checkout resolution, Darwin boilerplate,
dependency checks, raw message conventions, or custom linking behavior.
Installers run during both bootstrap and update and must be non-interactive,
idempotent, and safe to repeat.

### Homebrew and Mise

`homebrew/install.sh` only makes Homebrew available.
`homebrew/_availability.sh` owns executable and prefix discovery shared by
setup and Zsh. `homebrew/_maintenance.sh` removes known legacy taps only when
they no longer own installed packages. `homebrew/_bundle.sh` owns Brewfile
reconciliation and the narrow trusted-tap list.

Placement rules:

- System binaries, libraries, casks, fonts, MAS apps, and taps belong in
  `Brewfile`.
- npm, PyPI/pipx, Ruby gem, Go module, and comparable language-package CLIs
  belong in `mise/config.toml`.
- A third-party Homebrew formula needs its tap and formula in `Brewfile` and
  its tap in the `homebrew/_bundle.sh` trust list.
- Regenerate `mise/mise.lock` through Mise from the repository root; never edit
  resolved versions or checksums manually.

## Domain contracts

### Checkout root

`dotfiles-root.symlink` is the only checkout-root interface. It resolves
symlinks and returns the physical checkout containing an anchor, keeping
commands local to the invoking worktree. `--install` repairs
`~/.dotfiles-root` and refuses to overwrite a regular file or directory.

Public adapters source `_scripts/adapter-checkout.sh`. Set `ADAPTER_ANCHOR` when
`$0` is not the real source, as in Zsh startup. Prefer the installed resolver
and fall back to the sibling repository resolver; never reintroduce fixed
`~/.dotfiles` assumptions.

### Zsh startup

`zsh/zshrc.symlink` resolves the checkout, exports `DOTFILES_ROOT`, and sources
`zsh/_startup.zsh` once. Startup owns this order:

1. Establish workspace defaults; load optional `~/.localrc`, then `.commonrc`.
1. Resolve Homebrew; initialize unique `PATH`, `MANPATH`, `fpath`, and autoloads.
1. Source sorted visible `path.zsh` files.
1. Source other sorted visible topic `*.zsh` files except completions and the
   authoritative prompt.
1. Source `zsh/prompt.zsh` as the sole prompt.
1. Run `compinit` once and source sorted completions.
1. Load optional syntax highlighting last.

Reloading must not duplicate paths, hooks, or private implementation state.

### OpenCode and OCX

OpenCode is a terminal-first, Mise-managed CLI launched through OCX. The shell
selects `regular` with `OCX_PROFILE`; public entrypoints use `ocx opencode`, and
explicit profile aliases may pass `-p`.

`opencode/install.sh` initializes the `kdco` registry, installs its workspace
when the receipt is absent, and links dotfiles-owned editable entries into
`~/.config/opencode`.

Dotfiles may own `agents`, `commands`, `skills`, `tools`, managed profile
directories, `ocx.jsonc`, `opencode.jsonc`, `tui.jsonc`, and other entries
explicitly added to the installer contract. OCX owns `.ocx`, `plugins`,
`package.json`, `.gitignore`, and `profiles/default`; keep those generated paths
out of Git.

Create `regular` before specialized profiles. `go` and `boost` are installed
with `--clone regular`; keep their profile instructions, OCX policy,
permissions, MCP servers, and researcher shell policy aligned with that
baseline. Specialize only model routing and model-specific options unless a
profile contract is intentionally changed and documented.

When adding or changing a managed profile or entry, update these together:

- `opencode/install.sh`
- `opencode/README.md`
- `tests/opencode_install_test.sh`

Model IDs and variants must come from the current live catalog:

```bash
opencode models <provider> --verbose --pure
```

Provider-specific variants are request overlays. Do not invent a universal
variant or assume that `fast`, `max`, or a reasoning level exists for every
model.

### SSH and SOPS

`ssh/install.sh` may repair permissions, link the tracked config, preserve
`~/.ssh/config_local`, and move a conflicting config to a numbered backup. It
must never generate, rotate, delete, upload, or print credentials.

`bin/ssh-key-create` is the explicit key-generation boundary. It accepts
`default`, `personal`, or `work`, defaults to Ed25519, supports `--rsa`, and
refuses to overwrite either half of a pair.

`sops/install.sh` may create the age directory and repair safe permissions. It
must never generate, rotate, delete, or print identity material.

`bin/sops-key-create` is the explicit age-generation boundary. It writes an
identity and matching recipient for `default`, `personal`, or `work` and
refuses to overwrite existing files.

## Style, documentation, and dependencies

- Follow neighboring language conventions and preserve compatible shebangs.
- Quote paths and expansions unless intentional splitting is documented.
- Prefer `printf` to non-portable `echo` behavior.
- Format POSIX/Bash shell with `shfmt -i 2 -ci -bn` and lint with
  `shellcheck`. Never run `shfmt` over Zsh-only syntax.
- Format Markdown with the Mise-managed `mdformat`, which includes
  `mdformat-gfm` and `mdformat-frontmatter`. A bare formatter can damage GFM
  tables and skill frontmatter.
- Keep `README.md` concise but self-contained for installing, operating, and
  discovering the public surface.
- Keep `AGENTS.md` actionable for automated contributors and this file
  reference-oriented.
- Do not add license, contribution, or changelog sections to `README.md`.

## Delivery checklist

Before an authorized commit or push:

- [ ] Requested behavior is implemented in the owning source.
- [ ] Relevant fixtures cover the new contract.
- [ ] Focused tests pass; the full suite was used when shared behavior changed.
- [ ] `git diff --check` passes.
- [ ] Documentation matches the implemented state.
- [ ] No secrets, generated runtime state, or unrelated changes are staged.
- [ ] The commit message is concise and imperative.
- [ ] The requested branch and remote are explicit.
- [ ] Local and remote divergence is verified after pushing.

For an explicitly authorized direct publication to `main`:

```bash
git add <confirmed-paths>
git commit -m '<imperative message>'
git push origin main
git -c core.fsmonitor=false rev-list --left-right --count origin/main...main
git -c core.fsmonitor=false status --short --branch
```

The expected final divergence is `0 0`, and the worktree should be clean.

## Troubleshooting reference

- `fsmonitor_ipc__send_query` during Git inspection: rerun the Git command with
  `-c core.fsmonitor=false`.
- `/var` versus `/private/var` path mismatches in macOS fixtures: compare
  physical `realpath` results.
- A fixture unexpectedly reading the real OpenCode configuration: override
  `HOME` and `OPENCODE_CONFIG_DIR` explicitly.
- A newly added topic not loading: inspect `_scripts/topic-catalog` output and
  check visibility, reserved names, filename, and executable mode.
- An installer changes state on every run: reproduce with its fixture and move
  comparison/link ownership into the shared helper contract.
- A Homebrew bundle requires a third-party tap: declare the tap in `Brewfile`
  and add only that tap to the trusted list.
- A model variant is rejected: refresh and inspect that model's live verbose
  catalog rather than guessing a variant name.
