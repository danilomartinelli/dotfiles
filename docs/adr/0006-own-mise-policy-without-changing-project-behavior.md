# Own Mise policy without changing project behavior

One private POSIX executable, `_scripts/mise-policy`, owns Mise invocation
policy: it runs protected commands, regenerates explicitly selected lock
entries, and emits configuration for shell initialization and CI. Shell and
Python callers use the same interface. It is not written in Python because it
must help install the runtime Python would need.

Managed maintenance consumes exclusively `mise/config.toml` and its lock from
the checkout its caller resolved
([ADR-0004](0004-each-entry-point-resolves-its-own-checkout.md)), or from the
controlled upgrade's staged copies. External configuration and inherited
selectors cannot change that selection. Shell initialization instead preserves
project discovery, global configuration fragments, and intentional personal
overrides: sharing policy does not mean forcing every project to use the
checkout's environment. `_scripts/trusted-roots` remains the source of trusted
roots; the module applies them and adds trust for staged configuration only to
the invocation that needs it.

Reconciliation consumes recorded versions and never regenerates the lock. A
missing or incompatible resolution stops it with guidance rather than resolving
a newer release. The controlled upgrade of
[ADR-0001](0001-controlled-software-upgrades.md) is the only automatic writer,
deliberate manual regeneration by the owner remains supported, and write access
is granted only to the explicit regeneration operation, never to an environment
reused by later queries or installs.

Ordinary Mise execution inside this checkout, including `mise exec` launched by
an editor, follows the same rule: it consumes recorded resolutions, may install
a configured tool at its recorded version, and stops on a missing or
incompatible one. A wrapper cannot cover those calls, so a versioned root
`.mise.toml`, generated by the module and compared whole by a contract test,
carries only the local policy. It protects a fresh checkout without a setup
step and stays out of the configuration linked as global, where it would change
how unrelated projects use their own lockfiles.

## Consequences

The protection covers calls inside the checkout and managed operations. The
installer links the global `mise.lock` to this checkout's lock, so with global
`lockfile = true` an ordinary `mise exec` outside the checkout can auto-install
a missing global tool and rewrite the tracked file through the link. That write
path is accepted; closing it while preserving project behavior needs a separate
decision.

Inside a worktree, ordinary calls keep normal discovery and may consume the
global configuration and lock linked to the active checkout. Only managed
operations select the caller's checkout.

A failure to prepare configuration or trust stops the managed operation and CI.
During shell initialization it prints a diagnostic, skips Mise integration and
keeps the shell usable with its previous environment; partial output is never
applied. CI receives its environment from the module rather than keeping a
second policy in workflow variables.

The interface and its isolated characterization are described in
[Mise maintenance](../../mise/README.md).
