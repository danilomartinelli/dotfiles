# Own Mise policy without changing project behavior

For [issue #63](https://github.com/danilomartinelli/dotfiles/issues/63), one
private POSIX executable owns Mise invocation policy. It runs protected
commands, regenerates explicitly selected lock entries, and emits configuration
for shell initialization and CI. Shell and Python callers use the same
interface. Depending on Python here would require the runtime this module must
help install or start.

Managed maintenance consumes exclusively `mise/config.toml` and its lock from
the checkout its caller resolved, or from the controlled upgrade's staged
copies. External configuration and inherited selectors cannot change that
selection. Shell initialization instead preserves project discovery, global
configuration fragments, and intentional personal overrides. Sharing policy
does not mean forcing every project to use the checkout's environment.

Callers resolve their own checkout and pass it explicitly, as required by
[ADR-0004](0004-each-entry-point-resolves-its-own-checkout.md). A staged
declaration directory is a separate input: it contains configuration and lock
copies, not the checkout's helpers. `_scripts/trusted-roots` remains the source
of trusted roots; the module applies them and adds trust for staged
configuration only to the invocation that needs it.

Ordinary Mise execution inside this checkout, including `mise exec` launched
by an editor, must also preserve the generated lock. A wrapper alone cannot
cover those calls. A versioned root `.mise.toml`, generated by the module,
contains only the local policy. A contract test compares the whole file with
the module's canonical output. This protects a fresh checkout without a setup
step and keeps the policy separate from configuration linked as global.

This protection is limited to calls inside the checkout and managed operations
through the module. The installer links the global `mise.lock` to the active
checkout's `mise/mise.lock`: they are the same repository-owned lock, not locks
belonging to different projects. With global `lockfile = true`, an ordinary
`mise exec` outside this checkout can auto-install a missing global tool and
rewrite that tracked file through the link. The root `.mise.toml` is not loaded
there. This decision accepts that remaining write path; it does not promise
that every Mise invocation preserves the repository lock.

The reason to keep the local policy out of global settings is its effect on
other projects, not ownership of the global lock. A global `lockfile = false`
would also disable unrelated projects' lockfiles unless they override it.
Closing the remaining write path while preserving project behavior requires a
separate decision about global lock protection. CI receives its environment
from the module before installing runtimes rather than maintaining a second
policy in workflow variables.

Reconciliation consumes the recorded versions and never regenerates the lock.
A missing or incompatible lock stops reconciliation with guidance. The
controlled upgrade remains the only automatic writer within managed maintenance,
while deliberate manual regeneration by the owner remains supported. Writes
from ordinary external calls are the accepted gap above, not owner-selected
upgrades. This clarifies the automatic-write boundary in
[ADR-0001](0001-controlled-software-upgrades.md); it does not turn a
failed reconciliation into permission to select new releases. The module grants
write access only to the explicit regeneration operation, never to an environment
reused by later queries or installs. The upgrade retains its checks for changes
outside the selection and concurrent source edits before publishing staged files.

Failure to prepare configuration or trust stops the managed operation and CI.
During shell initialization, a preparation or activation failure produces a
diagnostic on stderr and skips Mise integration while keeping the shell usable
and preserving its previous environment. Partial output must never be applied.

Tests exercise the executable interface with isolated checkouts and a shared
fake Mise contract, including the selected configuration, trust, working
directory, and lock effects. The shell and Python callers cannot maintain
different interpretations of the fake. These fixtures validate repository
behavior without installing software on the Mac.

Validation of the local protection must distinguish the working directory from
the lock's destination: with the global lock linked into a fixture checkout,
ordinary execution inside that checkout must leave its bytes unchanged.
Execution outside it remains outside the preservation guarantee, even though
the destination is the same file. Real-Mise characterization must exercise a
missing tool; an already installed tool can hide this write path.

This decision is accepted; the implementation remains pending in issue #63.
